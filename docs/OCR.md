# 截图 + OCR：能做什么，不能做什么

> 这一页不是"功能介绍"，而是**实测结论**。数据来自本仓库在一台中文 Windows 11 上的真实测量，
> 结论直接决定了代码里为什么把 OCR 放在"辅助"位置而不是主读取通道。

## 一、能力清单（实测）

| 能力 | 结果 | 说明 |
|---|---|---|
| Windows 自带 OCR（`Windows.Media.Ocr`） | ✅ 可用，**零依赖** | 不用装 tesseract，不用联网，系统自带 |
| 可用语言 | `en-US`、`zh-Hans-CN` | 引擎要按语言创建；**必须预先加载 `Windows.Globalization.Language` 这个 WinRT 类型**，否则会误判成"机器不支持中文" |
| 识别耗时 | 约 **270–340 ms** / 1719×924 窗口 | 对"每几十秒看一眼"的监工场景完全够用 |
| 每个词的**精确矩形** | ✅ 有（x/y/w/h） | 这是 OCR 最有价值的部分：**位置** |
| 不抢焦点截窗口（`PrintWindow`） | ✅ 可以 | 后台窗口也能截，不需要激活 |
| **Chromium/Electron 截图** | ⚠️ **必须 `flag=2`（`PW_RENDERFULLCONTENT`）** | `flag=0` 截出来是**全黑**（实测 mean=0/std=0）；`flag=2` 才有画面（mean≈181/std≈86）。驱动会自动先试 2 再试 0，并用像素方差判定是否黑屏 |
| OCR 读**英文/代码** | ✅ 准确 | 例：`npm test failed exit code 1` 逐词坐标完整正确 |
| OCR 读**中文界面** | ❌ 保真度差 | 见下表 |

## 二、中文 OCR 到底有多准（两组实测）

**结论先说：识别质量强依赖"文字被渲染成什么样"。**同一台机器上：

### A. 干净的大字号正文（模拟 agent 回答的区域）——**相当准**

`node scripts/verify-ocr.mjs` 会画一张 ground truth 图再识别，实测 `zh-Hans-CN` 引擎：

```
ground truth：赛博监工正在读取对话框内容
OCR 结果    ：赛 博 监 工 正 在 读 取 对 话 框 内 容     ✅ 全对（只是被拆成单字）

ground truth：第 3 轮判定：continue（置信度 0.90）
OCR 结果    ：第 3 轮 判 定 continue （ 舀 信 度 0 ． 90 ）  ⚠️ 置信→舀信

ground truth：输入消息…   发送   停止生成
OCR 结果    ：输 入 冫 肖 息 发 送 停 止 生 成            ⚠️ 消→冫肖
```

→ 读**正文级**文字（14–20px、高对比、成段排版）：可用，但**会有零星错字**，
适合"知道它在说什么"，**不适合当证据**。

### B. 密集的小字界面（真实窗口截图）——**基本不可用**

对一张真实的浏览器窗口截图（多个中文标签页 + 图标 + 小字）：

```
天 气 》 × Deep × 赛 博 《 × 0 AKSI ×      ← 实际是标签页标题，字被拆开、顺序错乱
囗 科 研 / 囗 工 具 / 令 / 兮 / C 侖        ← 图标被当成汉字
```

→ 读**界面外壳**（标签页、按钮、图标、小字）：不可用。

### C. 英文/代码

```
npm test  failed  exit code 1     ✅ 逐词正确，且每个词都有精确矩形
```

→ 英文与代码风格文本识别质量最好（包括中文系统上的 `en-US` 引擎）。

## 三、所以它在项目里的定位

```
读对话内容：  磁盘会话（最准） → 剪贴板（准、快） → UIA（次之） → OCR（最后手段，仅当上面全失败）
取位置信息：  UIA（有则用） → OCR 词矩形（总是可用）→ 配置里的相对坐标
辅助证据：    截图附进报告，主人早上能直接看到当时屏幕
```

具体到代码：

- `human-sim` 适配器的读取阶梯是 **磁盘 → 剪贴板 → UIA**；OCR 作为最后一级
  （并会在日志里标注 `readVia: 'ocr'`，让判定者知道这段文本不可全信）。
- 截图能力（`driver.capture`）已经可用：自动先试 `PW_RENDERFULLCONTENT` 再退回整窗，
  并用像素方差判定黑屏（`std < 3` 视为失败）。
- **自检命令**（会打印你机器上的准确率与截图结果，并把样本图留在指定目录）：

  ```bash
  node scripts/verify-ocr.mjs --dir .cyber/shots
  ```

  在**你的机器**上重跑一遍很有必要：识别模型随 Windows 版本与语言包变化，别人的结论不一定适用。

## 四、为什么没有把 OCR 当主通道

用户的直觉（"截图 + OCR 就够了"）在**位置**这一半是对的，在**文本保真**这一半不成立：

1. **文本渠道本来就存在且更准**：会话日志、剪贴板、UIA 都能拿到**零错字**的原文，
   OCR 是"从像素猜字"，天生有损；
2. **中文尤其吃亏**：实测同一张图，剪贴板能拿到完整正确的对话文本，OCR 只能拿到碎片；
3. **判定依赖文本语义**：监工要把"最后一次回答"和方案对照着判断，错字会直接影响判定质量；
4. **但位置只能靠图像/UIA**：所以 OCR 的价值集中在"哪个区域有文字/按钮在哪/输入框在哪"，
   这恰好能治"点不准输入框"这类真实故障（本仓库在拟人通道自检里就踩到过）。

## 五、如果你要在此基础上继续做

- **多模态判定**：把截图交给支持视觉的模型，让它"看着屏幕"判断 agent 是否还在跑、
  是否在等人、有没有报错弹窗。这是 OCR 之外更省事的路线，但依赖模型能力与额度。
- **OCR 定位输入框**：把 `options.composerText`（例如英文界面的 `"Message"`/`"Ask"`）交给 OCR 定位，
  命中后点它的矩形中心——对**英文界面**可靠；中文界面建议仍用相对坐标 + 焦点探针。
- **更强的 OCR**：换 PaddleOCR / RapidOCR（有 ONNX 版本，可离线）。代价是引入依赖或模型文件，
  与本项目"零运行时依赖"的取舍冲突，所以没有默认启用。
